## 本机API核对及停止原因

只读检查当前Steam 1.1.2.8-ffc2de0-sw原版Timberborn.WeatherSystem.dll、Timberborn.HazardousWeatherSystem.dll的相关三个服务；程序集元数据版本均0.0.0.0，未做全程序集反编译。

1. WeatherService.IsHazardousWeather从GameCycleService.CycleDay与HazardousWeatherStartCycleDay比较得到；后者为TemperateWeatherDuration+1。周期长度为正常时长+灾害时长。因此仅广播开始/结束事件不能同步改变周期判定。此为本机getter IL直接证据。
2. HazardousWeatherService.CurrentCycleHazardousWeather和HazardousWeatherDuration的setter均Private，getter Public；TemperateWeatherDurationService.TemperateWeatherDuration同样Private setter。完整方法名/访问级别只在这三个服务中定向核对，不据此声称整个游戏不存在其他扩展接口。
3. StartHazardousWeather和EndHazardousWeather的IL仅创建并Post相应Started/Ended事件，不更新上述属性或CycleDay。不能把它们当作完整状态切换API。
4. SetForCycle重新随机选择灾害并计算持续时间，然后发布Selected事件，并非按用户指定类型/时长设置；不把重新随机化冒充修改命令。
5. 上游[Targets/Common.targets](https://github.com/datvm/TimberbornMods/blob/a10fb8c97dec090df1cef28f9efa9dd2ba524f4f/Targets/Common.targets)明确引用GameAssemblyPublicizer/out/common和IgnoresAccessChecks.cs；其源码属性赋值不是对本机未经修改DLL的公开可访问性证明。上游manifest最低0.7.0.0，不能假定适用于本机1.1。

结论：天气切换/时长未达到本轮“可靠原生入口、范围小、无需改变其他核心行为”的自主实施门槛，按停止条件不编写生产代码。不直接反射私有setter，不引入公开化程序集、Harmony、日历跳转、自动保存重载或只读替代功能，也不扩展为长期底层调查。

下一步需先确认是否接受范围受限的非公开接口/补丁方案及天气与周期同步语义，再作小范围设计；本轮没有证明哪种替代路线足够安全，也不预先要求某个框架。用户未授权选择前保持天气/灾害未实现，不显示可用状态。

## 补充授权后：本周期灾害总时长实现

以上“不编写生产代码/尚未实施”是初步调查检查点；用户随后明确允许反射或其他小型非公开访问，并要求不能仅因private停止。本节为当前实现状态。仅推进一个功能点：编辑本周期已选原版干旱/恶水的总持续天数，不切换类型/阶段，不推进日期，不改变正常期长度，不覆盖后续周期。

### 完整原生调用链补证

- GameCycleService.OnDaytimeStart → private StartNextDay：CycleDay加一，比较private _cycleDurationInDays，超出后调用private StartNextCycle，最后Post CycleDayStartedEvent。
- StartNextCycle：先Post旧CycleEndedEvent，Cycle加一、CycleDay设1；对每个ICycleDuration.SetForCycle生成本周期参数，汇总DurationInDays写_cycleDurationInDays，再Post CycleStartedEvent。HazardousWeatherService.SetForCycle选择类型、计算时长、Post Selected事件；HazardousWeatherHistory监听Selected追加记录并统计周期数/连发数。
- WeatherService.OnCycleDayStarted只在CycleDay等于TemperateWeatherDuration+1时调用StartHazardousWeather；OnCycleEndedEvent在灾害时长大于0时调用EndHazardousWeather。两者分别广播Started/Ended，不单独修改日历。
- WeatherPanel.UpdatePanel/SetHazardousWeatherUI每次取原生时长、PartialCycleDay计算剩余和进度；不是修改器自己的倒计时。原生面板按自身刷新节奏更新，暂停时是否立即重绘仍待实机。
- HazardousWeatherService.Save保存实际HazardousWeatherDuration及原生类型；GameCycleService.Save保存周期/日期，Load从ICycleDuration重新求和恢复缓存。因此不能只改时长而留下旧缓存。本功能复用原生保存数据，不新增游戏存档字段、序列化器或自动保存/重载。

上述均为当前三个相关程序集的指定类型/方法IL证据，不把反射访问能力本身当作状态一致性证明。

### 最小实现与限制

WeatherModule在PostLoad后按需读取，Unload释放场景引用；通过现有Bindito绑定，在UI点击同步执行，不加Tick、后台任务或Harmony。私有成员仅HazardousWeatherDuration的setter，以及GameCycleService._cycleDurationInDays和只读枚举_cycleDurations。setter IL只赋整数，无事件；两个字段值在同一次调用内更新，不当作全引擎事务/锁。暂停只是防止自然日推进的操作条件，不声称锁住其他Mod。

操作前要求精确游戏/Unity/平台版本匹配、全局启用、SpeedManager.CurrentSpeed=0且Unity Time.timeScale=0；重新读取周期号、日、正常/灾害时长、已注册来源总和与缓存。来源必须恰好为当前原生TemperateWeatherDurationService和HazardousWeatherService，未知天气或额外来源拒绝；不宣称通用第三方天气兼容。

输入整数1～1000；新周期总长=旧总长-旧灾害时长+新时长。缓存必须等于来源总和及正常+灾害时长；不允许使当前日期超出新周期，不允许原灾害总长为0。这样不会立刻跨越正常/灾害边界或周期结束，也不必模拟Started/Ended或Selected事件。后续自然到日、开始/结束仍由原版调度。

保持原选定历史，不重复Post Selected，否则会重复计数；本机History.GetCyclesCount及CalculateStreakFromHistory按天气ID而非时长大小计数。历史中的选定时长不会回写为手动覆盖值，当前生效/保存时长以HazardousWeatherService为准。此限制需随第三方读取历史的行为实测，不能宣称所有扩展Mod都兼容。

两项无事件的原生整数赋值遇访问异常时尝试恢复原值，之后仍报告未确认而非成功；不重新尝试用户请求。执行后回读周期/日期/类型/两项时长/缓存和来源总和，全部符合才显示回读确认。失败时提示检查实际状态，没有长期接管调度器或自动修复循环。

天气页和灾害页共享相同面板：刷新当前天气及本周期已选灾害，设置总时长；显式标注非剩余时间及尚待实机。不改Config Schema1，不执行预留WeatherOverride字段，输入/执行状态不入配置。和库存/科研的一次性命令一致，关闭全局只阻止下一次请求，恢复默认不撤销已修改周期。
