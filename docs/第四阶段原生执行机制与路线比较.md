# 第四阶段：原生执行机制与候选路线比较

2026-11-08，功能基准e0e804e；本轮只读解析安装游戏PE元数据/IL，没有把游戏DLL加载执行到调查宿主，没有写入实现或补丁。结论 **CONDITIONAL GO**：已补强正常物流/生产/施工的实际调用关系，仍没有可批准写入的完整互斥及归因证明。

## 1. 版本、范围和证据

游戏1.1.2.8-ffc2de0-sw、Unity6000.5.11f1；既有8项程序集指纹一致。本轮补记TickSystem、Multithreading、BehaviorSystem、Workshops、ConstructionSites、InventoryNeedSystem的当前SHA256，见《第四阶段调度调查程序集指纹.json》，用于复核本次新增证据，不谎称它们此前都有比较基线。以下类型名均在当前程序集实际存在。

“直接”=所列方法IL含明确调用；“推导”=组合调用链后的条件判断；“未证”=尚未完成穷举或实机同步取证。局部方法没有锁，不等于整个原生系统没有其他保护。本轮未穷举全部第三方、全部原生并行任务或所有库存写入点。

原始定向分析留本机work/stage4-*.txt；只分析相应类型和相关方法，不提交完整IL、游戏文件、用户日志或存档。没有联网下载或运行第三方Mod/工具；“其他Mod可复用方式”没有新的外部实现证据，不宣称已验证任何社区队列方案。

## 2. 行为与执行阶段：新确认的调用链

### 2.1 实体Tick与海狸行为

**直接，Timberborn.TickSystem.dll、Timberborn.BehaviorSystem.dll**：

TickableEntityBucket.TickAll → TickableEntity.Tick → TickTickableComponents → MeteredTickableComponent.Tick → TickableComponent.Tick。BehaviorManager.Tick中先TickRunningExecutor，再在没有运行执行器时ProcessBehaviors；ProcessBehavior调用Behavior.Decide。TickRunningExecutor使用ITickService.TickIntervalInSeconds计时，调用IExecutor.Tick(dayNightCycle.FixedDeltaTimeInHours)。

BehaviorManager并非用于任意Mod操作的命令队列：它保存当前行为、返回行为和执行器，并按Decision进行恢复/等待。不能把“下一Tick再次决策”当作“一次请求只执行一次”的库存提交凭据。

**线程边界**：这些已检查方法是同步调用，没有在该段把库存操作包装为任务；但组件可能另外调度任务，不能仅凭同步栈认定整个进程没有并发。

### 2.2 从仓库取走资源

**直接，Timberborn.Carrying.dll**：

CarryRootBehavior.Decide → TryToRetrieve。必须已有容量预留，且有来源库存的物品预留；根据来源Accessible启动WalkToAccessibleExecutor，抵达后CompleteRetrieval。

CompleteRetrieval保存自己的StockReservation，先GoodReserver.UnreserveStock；固定量使用原GoodAmount，否则RecalculateAmountToRetrieve；ConsumeGood=true调用Inventory.TakeConsumed，否则TakeExisting。之后CreateCarriedGood、GoodCarrier.PutGoodsInHands，再尝试送货。

不是任意减少命令：绑定真实海狸、来源、搬运能力、目的地/容量预留和行为状态。释放的是该海狸自己的预留，不提供解开其他物流任务预留的授权。

### 2.3 搬运进入仓库

**直接，Timberborn.Carrying.dll**：

Decide → TryToDeliver：要求GoodCarrier.IsCarrying；没有容量预留时由GoodCarrierCapacityReserver.ReserveCapacityForCarrier寻找/预留真实目的地；步行抵达后CompleteDelivery。

CompleteDelivery保存CapacityReservation，先UnreserveCapacity，再HasUnreservedCapacity；根据CarriedGood.Type分支GiveProduced或GiveExisting，成功返回后EmptyHands、ReleaseNow；空位不满足时ReleaseNextTick。

不是凭空增加入口：需要真实已携带物资以及相匹配的预留。手工创建CarriedGood或虚构来源会绕过守恒与行为状态，不作为候选方案。失败时原生可能安排下一Tick重试，这种原生搬运生命周期也不等同于Trainer允许自动重试。

### 2.4 生产原料消耗与产品产生

**直接，Timberborn.Workshops.dll**：

BehaviorManager.TickRunningExecutor → IExecutor.Tick → ProduceExecutor.Tick → Manufactory.IncreaseProductionProgress。

ProduceExecutor校验工作地点、生产中、阻挡、结束时间和IsReadyToProduce；按工人速度增进度。IsReadyToProduce检查配方、原料、产品未预留容量、燃料、动力与效率。

- IncreaseProductionProgress → RefillFuelAndTakeIngredients：需要燃料时TakeConsumed一单位；本周期首次正进度先设置_ingredientsConsumed，再逐项TakeConsumed配方原料，然后UpdateGoodRegistry。
- 完成周期时FinishProduction逐项GiveProduced配方产品，再处理科研点、燃料、进度重置及ProductionFinished事件。

未在这些直接方法中发现通用库存事务、操作Id或库存互斥锁。并非所有生产建筑都使用该配方路径，本报告不扩大为全游戏穷举。多资源逐项调用不是事务：订阅者抛异常可能中断后续原料/产品和配方状态；不能借生产接口实现任意资源、数量的原子注入。

### 2.5 建筑材料交付与施工

**直接，Timberborn.BuilderHubSystem.dll、Timberborn.ConstructionSites.dll**：

BuildingJobProvider.GetJob → ConstructionRegistry.GetJobs → ConstructionJob.StartConstructionJob。后者检查所属地区、工地IsOn及可达路径；可以施工则启动BuildBehavior，否则寻找ClosestObjectWithNeededGood并StartNeededMaterialsDelivery。

StartNeededMaterialsDelivery根据真实来源、工地Inventory与海狸搬运能力求AmountToCarry；对来源调用GoodReserver.ReserveNotLessThanStockAmountConsuming，对工地调用ReserveCapacity。后续进入上述CarryRootBehavior流程。

因此建筑材料的消费分类出现在**从来源取货的TakeConsumed分支**；不能预设“工地完工时再统一TakeExisting”。BuildExecutor.Tick只在IsOn、HasMaterialsToResumeBuilding和时间允许时IncreaseBuildTime。

ConstructionSite.FinishIfRequirementsMet通过原生校验后MarkAsFinished；OnExitUnfinishedState停用施工组件及其Inventory。当前检查的完工链没有再扣一次施工库存。先前实机完成建筑仍有停用的施工材料库存也与此相容；原生材料统计/返还机制不能靠清空库存模拟。ConstructionSiteInventoryInitializer以BuildingCost创建允许资源和容量，不是普通仓储写入入口。

这条流程遵循真实材料与任务，不支持任意凭空资源注入。施工目标继续排除。

### 2.6 饮食/饮水预留的补充

**直接，Timberborn.InventoryNeedSystem.dll**：InventoryNeedBehavior.Decide读取当前GoodReserver.StockReservation，寻找合适物资后ReserveExactStockAmount，再用WalkInsideExecutor；抵达后ConsumeGood → RemoveGoodFromInventory并施加需求效果。

说明正常需求行为确有可能形成物品预留；不能因为本轮有限诊断及两个保存时点没抓到正值，就断言它不使用预留或诊断已覆盖所有正值。本轮没有追完整RemoveGoodFromInventory的后续消费实现，消费通知/异常以已确认的库存公共链为边界。

## 3. 调度入口候选：更精确的边界

### 3.1 Tick窗口

**直接，Timberborn.TickSystem.dll**：TickableBucketService.TickNextBucket按索引分支：Singleton桶调用ITickableSingletonService.TickAll，其他桶调用TickableEntityBucket.TickAll；不是在每个桶中都先等待并行完成再执行实体。

TickableSingletonService.TickAll内部才是FinishParallelTick → TickSingletons → StartParallelTick。StartParallelTick开始调度工作，之后其他实体桶会被推进。由此**不能把实体Tick天然视作上一并行已全部结束的窗口**；是否涉及相同库存的实际访问仍未证。

候选仍是TickSingletons调用ITickableSingleton.Tick的局部同步段。当前IL显示其前有IParallelizer.Wait、后开始新并行，但尚未证明所有库存参与者属于这个Parallelizer、所有事件不重入、其他系统不会另开工作或在该回调安排任务。没有补齐这些证据前不授权。

### 3.2 新确认的公开阶段读数

**直接**：ITickableSingletonService及实现公开getter `ParalleTicklIsFinished`（游戏原拼写）、`IsStartingParallelTick`，返回对应原生字段。

下一步最小只读补证可以在原生注册与依赖生命周期审查后，让有限探针记录这两个读数和UI/Tick事件。它们是阶段观察，不是库存锁、任务所有权或跨方法临界区证明；不能只检测某一时刻true就直接写入。本轮未新增依赖注入、未在当前游戏中读取这些标志，避免把尚未实测的新DI当成功结果。

### 3.3 并行任务队列

**直接，Timberborn.Multithreading.dll**：Parallelizer有Schedule、StartScheduling、StopScheduling和Wait；StartScheduling拒绝已在调度，并检查未完成任务。Wait先ThrowIfNotMainThread，用SpinWait和Interlocked观察_pendingTasks，随后检查异常/剩余任务。

ScheduledTask.Run有内部Monitor保护任务调度/完成状态，RunTask实际调用ITaskRunner.Run。LockingQueue和ScheduledTask内部锁/版本字段服务于工作队列/池化任务，不是锁定Inventory，也不为库存变更提供事务版本。存在Schedule不证明请求会回到主线程安全窗口，不能把库存Action直接送入工作任务来解决竞争。

**未找到已证明可复用的串行库存命令队列**。这是所检查服务和调用链的限定结论，不是全引擎不存在队列的证明。CommandLine程序集元数据只有CommandLineArguments等启动参数类型，不因名字Command就当运行期库存命令入口。InventorySystem所检查类型没有可确认的通用事务服务。

### 3.4 UI、生命周期与探针范围

UI仍是UIToolkit按钮直接回调；既有37条探针同线程结果只观察本Mod UI/Tick，不能证明原生物流或所有并行阶段的时间关系。本轮没有新开探针或给原生方法打补丁，不重复相同同线程取证来冒充新证明。

场景卸载应取消未开始的本Mod意图，并清引用；已进入调用而归因不明的结果保留Indeterminate，不能在下一场景补发。当前没有执行器/排队命令，所以这一点仍是执行契约而非运行时已测保证。暂停、PostLoad、Unload和FinishFullTick都不是可随意使用的库存锁；本轮没有调用后者。

## 4. 预留、事件与归因

重新核对Inventory.GiveInternal：CheckCapacity → CheckUnreservedCapacity → GoodRegistry.Add → InvokeInventoryStockChangedEvents。TakeInternal：CheckIfHasStock → Subtract → CheckIfUnwantedStockDisappeared → 通知。没有看到该链的自动回滚或本次请求Id。

结合CarryRootBehavior可见，若事件在库存变化后抛异常，后续PutGoodsInHands/EmptyHands可能未运行；这是**静态控制流风险**，不是本轮故意注入或已观察到的资源重复/丢失Bug。不能借原生物流包装就声称具有事务保障。

全库存物品预留R与容量预留Q分别控制取出和在途空位；不能先解除他人的预留以获得写权限。原生转运释放自己的预约再调用接口，并不允许Trainer仿造一份预约。

异常结果契约不变：进入原生调用前明确拒绝才为Rejected；一旦调用已开始，异常、对象变化、并发/归因或回读不明保持Indeterminate，哪怕最终数值恰等目标。不得重试、补差或反向回滚。

## 5. 三条路线比较

| 维度 | 路线一：安全阶段直接原生接口 | 路线二：原生命令/任务调度 | 路线三：原生物流/库存服务 |
| --- | --- | --- | --- |
| 已有证据 | Give/Take检查及正常调用链直接；TickSingletons有局部Wait依据 | 已确认Parallelizer工作调度，未找到串行库存提交入口 | Carry/GoodReserver、生产与施工链明确 |
| 任意资源/数量 | 接口可接受已注册GoodAmount，仍须角色/限额/零预留门控；不能绕容量 | 未有能支持任意库存意图的已证API | 搬运需真实来源/目的/能力；配方需真实原料和特定产品，不支持任意凭空增减 |
| 并发安全 | **未证完整互斥**；不能在UI直接调用 | 任务队列锁不等于库存锁，可能在工作线程，未证 | 原生正常流程并不为外部强行调用提供安全上下文 |
| 身份/生命周期 | 自建短期原引用核验，Unload取消；第三方同对象重用仍不完备 | 还需队列自身场景/取消契约，当前无证据 | 真实海狸/行为/目标/预留生命周期，不可假造或长期借用 |
| 预留 | 首批完整零预留且无未知；读到零不自动授权 | 调度仍须执行时重读全库存，不能替代门控 | 自身预约会创建/释放，取消涉及行为所有权；不能替代零预留Trainer策略 |
| 守恒/任务 | 一次Add/Remove本来改变总量，不创建物流 | 语义未知，不能假设无任务/不变更预留 | 真实转运遵守来源物资；伪造来源会造成重复/丢失风险，禁止 |
| 一次请求/取消 | 需Mod内一次调用状态机；未实现，进调用后不自动重试 | 原生工作完成/池版本不是库存提交幂等键；取消/卸载未证 | 原生行为可跨Tick重试；没有外部请求至多一次和通用取消保证 |
| 异常归因 | void+同步事件，无事务凭据，严格保留Indeterminate | 队列只安排调用，不能解决调用后异常归因 | Take/Give与手持/配方状态可在事件中断，仍非事务 |
| 复杂度 | 中等，前提是证明执行窗口；不得以简单为选择理由 | 高且入口未证，当前不推荐新增工作任务承载库存操作 | 高，污染行为/物流状态，不符合任意数量编辑语义 |
| 第三方范围 | 仅明确原生普通仓储候选；私有字段/自定义规则/补丁不保证 | Mod任务和事件可能另行调度，不能扩大兼容 | 第三方搬运、需求或配方行为不自动兼容 |
| 实机可测 | 后续独立少量Add/Remove需本轮未满足门槛及新授权 | 先证明队列真实用途和线程，再谈实现；目前无方案可验收 | 可读观测正常搬运，但不能用伪任务来测试注入 |

**候选排序**：路线一仅作为待补证方向；它有直接库存语义和局部阶段依据，尚未达准入。路线二没有确认合用入口，不通过改用工作线程推进。路线三适合解释原生转运，不适合Trainer任意资源编辑；不给虚拟来源制造例外。没有一条路线本轮达到GO。
