## 3. P1：执行上下文与候选阶段

### 已追踪的调用链

- **Mod UI（直接源码）**：ControlStyles.ActionButton将Action交给UnityEngine.UIElements.Button基类；InventoryPanel扫描/刷新由这些回调直接调用。这里没有原生命令队列或Tick同步屏障。可以认定是UI事件调用路径，不能仅据此证明准确线程Id、PlayerLoop顺序或库存互斥。
- **Singleton更新（直接IL）**：SingletonLifecycleUnityAdapter.Update → SingletonLifecycleService.UpdateAll → IUpdatableSingleton.UpdateSingleton；LateUpdate也有独立链。它与UI回调、Tick不是同一接口，已检查链没有等待库存并行任务的保证。
- **Tick（直接IL，Timberborn.TickSystem.dll）**：TickerUnityAdapter.Update → Ticker.Update → ITickableBucketService.TickBuckets → TickNextBucket。TickNextBucket在相应位置调用ITickableSingletonService.TickAll，再TickableEntityBucket.TickAll → TickableEntity.Tick。桶内TickAll按实体调用；这不能排除组件内部安排并行任务。
- **并行Tick（直接IL）**：TickableSingletonService.TickAll依次FinishParallelTick → TickSingletons → StartParallelTick；FinishParallelTick调用IParallelizer.Wait、ThrowIfAnyPendingTasks，StartParallelTick调用调度和IParallelTickableSingleton.StartParallelTick。
- **完整Tick同步（直接IL）**：Ticker.FinishFullTick → TickableBucketService.FinishFullTick，后者会推进剩余TickNextBucket，随后调用ITickableSingletonService.ForceFinishParallelTick。它会推进模拟，不是只锁一个库存；ForceFinish还会发ForcedParallelTickFinished事件。
- **原生UI库存操作（直接IL，Timberborn.InventorySystemUI.dll）**：InventoryDebugFragment打开ModifyInventoryBox；其Open读取库存后PanelStack.PushOverlay，按钮回调 → GiveGood/TakeGood。其中还会修改SingleGoodAllower、使用GiveExistingIgnoringCapacity或TakeConsumed。不能把开发调试工具当Trainer安全实现；已检查方法内没有完整的线程互斥证明。是否Overlay外部还有暂停/同步约束，本轮未追完。
- **物流（已有当前指纹下IL）**：Carrying.CarryRootBehavior.CompleteRetrieval先释放自己的StockReservation再TakeExisting；CompleteDelivery先释放容量预留，重新检查后GiveExisting。调度来源和原生预留生命周期不可直接拿来当UI命令队列。
- **生产/仓储（有限证据）**：GiveProduced/TakeConsumed进入同一Inventory内部变更链；Stockpile完工启停改变物流注册。未穷举所有生产组件与线程，不能据已知个别调用推定所有写入串行。

### 候选点对比

| 候选接口/类型 | 已有同步依据 | 能否证明库存无并发冲突 | 场景失效与待验证 |
| --- | --- | --- | --- |

“一次请求至多一次”也没有现成已证原生操作Id：未来在场景内拥有请求Id、Queued→Revalidated→Invoking→Observed状态，一旦进入Invoking不再再次调用；禁止同库存重入。Unload取消所有未调用请求、释放引用；已开始但未确认的请求保留Indeterminate记录，不自动补发到新场景。此为设计约束，本轮未实现。

## 4. P2：全库存预留门控

### 可观察数据和公式

直接IL（Timberborn.InventorySystem.dll）：_storage、_reservedStock、_reservedCapacity为独立GoodRegistry。物品预留R(g)限制取走的实际货物；容量预留Q(g)保护在途货物空位，两者必须分别判断。

`UnreservedCapacity(g)=max(0,min(L(g)-A(g)-Q(g),C-S-QΣ))`。QΣ对所有资源求和，C/S是共享容量/实际总量；所以目标资源零预留不能代表全库存零预留。普通仓储还受StockpileSpec及SingleGoodAllower影响；SimpleOutputInventory/地区中心可有很大的共享上限但小的每资源限额及开局越限，继续排除首批写入。

- **直接公共入口**：Inventory.ReservedCapacity()无参数重载枚举整个容量预留GoodAmount列表；ReservedCapacity(g)读指定资源。不能只调用有参数重载。
- **物品预留观察**：未找到Inventory公开的整个_reservedStock直接枚举；可用R(g)=AmountInStock(g)-UnreservedAmountInStock(g)推导。Stock、AllowedGoods和注册资源可提供查询资源域。
- **并非冻结快照**：Goods.GoodRegistry.get_Goods调用ListExtensions.AsReadOnlyList包装原列表；只读视图不是原子、不可变化的库存快照。未经安全执行阶段直接枚举/ToArray并不能消除并发竞态。

### 条件化门控方案

在已经证明的安全执行上下文，针对**选中一个库存**执行：

1. 身份、完工、启用、原生Stockpile绑定和地区通过；未知/自定义规则拒绝。
2. 获取当前Stock、AllowedGoods、ReservedCapacity()全部条目，必要时结合当前注册资源Id域。只枚举该库存/资源定义，不扫描场景建筑。
3. 任何容量预留非零即拒绝；负数、溢出或条目失效不是“没有预留”，而是异常拒绝。
4. 对资源域内各g实时读A/U，要求0≤U≤A且R=A-U全部为0。核对原生总量与实际条目总量、资源定义及数量自洽。任何未知值、异常或不能建立完整资源域都拒绝。
5. 对目标资源再次读动态L、原生UnreservedCapacity、数量与允许规则，生成新计划；原生接口仍作为最终容量/预留校验，不拿自行求和替代原生约束。

**推导前提**：原生ReserveStock经库存量/未预留量校验，Take也不能扣预留；在正确初始化、仅遵守原生接口的不变量下，正物品预留应有相应实际库存，所以Stock资源域可支持推导。**不是无条件证明**：被其他Mod私有改写、隐藏未注册资源预留、破坏的不变量或同对象异常再初始化，可能无法从公共域完整观察。无直接_reservedStock枚举时，不能承诺检测任意损坏状态；首批必须排除无法确认状态来源的目标。没有完整证明或执行上下文时，当前正确结果仍是拒绝。

两类预留的公共观察路径已明确，但全库存门控的可靠性还依赖安全阶段、不变量及实机测试，不能标为已实现或全面解决。

## 5. P3：异常顺序与归因

直接IL：GiveExisting → GiveInternal → CheckCapacity → CheckUnreservedCapacity → GoodRegistry.Add → InvokeInventoryStockChangedEvents（先InventoryChanged，再InventoryStockChanged）。TakeExisting → TakeInternal → CheckIfHasStock → Subtract → CheckIfUnwantedStockDisappeared → InventoryChanged → InventoryStockChanged。取走过程的不受欢迎库存消失事件可能早于后续库存事件。任何订阅者异常都可能中断后续通知，变更不会自动回滚。

底层GoodRegistry.Modify更新条目、更新TotalAmount，再ValidateTotalAmount，未提供事务回滚；异常损坏/溢出或重入时不应承诺“要么完全没动，要么完整成功”。正常原生检查不足时在变更前拒绝，但一旦进入原生调用，本执行器未来不应仅凭异常类型推断未修改。事件可删除/替换对象，所以异常后先重新验证原引用，再考虑回读。

已检查Inventory及InventoryChangedEventArgs/InventoryStockChangedEventArgs：事件只有资源Id或GoodAmount+StockChangeType，没有本次命令Id、事务版本或提交凭据。未找到可用的原生事务归因接口；不能据此排除游戏其他系统存在版本概念，但当前没有可复用证据。

| 观测阶段 | 保守结果 |
| --- | --- |
| 明确未开始原生调用且安全检查失败 | Rejected |
| 合法意图无需变更且未调用 | NoOp |
| 只是生成计划 | Planned，无执行授权 |
| 已进入调用，异常/引用失效/回读失败/并发或归因不明 | Indeterminate；即使回读等于目标也不能改称Succeeded |
| 能证明正确对象、受控无交错执行、原生正常完成与通知、有效回读符合预期 | 才可候选Succeeded；本项目尚未具备整套证明 |

回读只能说明观察时的数量；同步事件或物流的额外+3/-3可让最终差额恰好等于请求，不能据此把全部变化归为Trainer。不自动重试、不补差、不反向回滚，不把Indeterminate记为普通“失败未生效”。如无法排除上述交错，未来必须保持Indeterminate，而不是放宽成功标准。
